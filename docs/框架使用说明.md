# 问答线实验使用说明

比较 T1–T6 对同一批 API 问答题的回答。题面只有 `Question` 和系统提示。标准答案、别名和出处只留在评分程序里。环境用 `uv`，不要提交 `.venv` 或 `.venvs`。本线不启动 OSIS 求解器。

```powershell
$env:OSIS_PARENT_REPO = "C:\path\to\osis-skill-enhance-main"
$env:OSIS_MODEL_API_KEY = "<key>"
$env:OSIS_MODEL_BASE_URL = "http://<gateway>/v1"
$env:WEKNORA_API_KEY = "<weknora-key>"
uv sync --python 3.13 --extra test
uv run python scripts/setup_framework_envs.py
uv run python scripts/create_knowledge_snapshot.py `
  --parent-repo $env:OSIS_PARENT_REPO `
  --output tmp\qa-knowledge-snapshot
```

快照是父仓库 `.agents/skills` 的完整副本，含模板画像和参考文件。`datasets/qa/questions.json` 不会复制进去。

## 怎么开跑

不调模型，只核对题号：

```powershell
uv run python scripts/run_dataset.py `
  --parent-repo $env:OSIS_PARENT_REPO `
  --architecture T2 `
  --skills-dir tmp\qa-knowledge-snapshot `
  --dry-run
```

一条正式任务。`--architecture` 换成 T1–T5。T6 另见下文，须先有父仓库 OpenCode。不写 `--model` 时，脚本默认仍是过期的 `deepseek-v4.1-flash-expires-on-0910`。和另外两条线对齐时写成 `deepseek-flash`。不写 `--variant` 时，思考强度按 `low` 发出：

```powershell
uv run python scripts/run_dataset.py `
  --parent-repo $env:OSIS_PARENT_REPO `
  --architecture T2 `
  --skills-dir tmp\qa-knowledge-snapshot `
  --model deepseek-flash `
  --variant low `
  --label formal-qa `
  --seed 0
```

六架构一起跑：

```powershell
uv run python scripts/run_campaign.py `
  --parent-repo $env:OSIS_PARENT_REPO `
  --architectures T1 T2 T3 T4 T5 T6 `
  --skills-dir tmp\qa-knowledge-snapshot `
  --model deepseek-flash `
  --variant low `
  --base-url $env:OSIS_MODEL_BASE_URL `
  --label formal-qa `
  --seed 0 `
  --jobs 1 `
  --resume
```

评分抽取最后一个 `FINAL ANSWER:`，按父仓库规则做准精确匹配。综合分是准确率 80% 加耗时效率 20%。失败、超时或没有最终答案的题记 0 分，仍计入分母。

## 并行还是串行

`--jobs` 只作用于 T1–T5，默认 1。这些架构不占 OSIS 端口，可以并行，但共用一个模型网关。正式对比建议 `--jobs 1`，避免网关 429 或 503 把耗时差进分数。

T6 复用父仓库已经打开的 OpenCode（默认 `http://127.0.0.1:4096`），campaign 始终串行。跑 T6 前先按父仓库方式执行 `opencode serve`，不要在实验仓库另起一套服务。

`--resume` 跳过已完成的当前 attempt。同一 label 再次开跑时，旧目录会先归档。结果在 `runs/` 和 `results/`，不进 Git。汇总方法见 [实验数据后处理.md](实验数据后处理.md)。

## 六个架构怎么接工具

题面相同：系统提示加 `Question`。标准答案不进模型输入。本线不启动 OSIS，也不把求解或验算做成工具。

T1–T5 读同一份技能快照，是父仓库 `.agents/skills` 的完整副本。T1、T2 用仓库 `.venv`，T3–T5 用 `.venvs/t3`、`t4`、`t5`。

| 架构 | 动作 | 本地技能怎么给 | 知识库怎么查 |
| --- | --- | --- | --- |
| T1 | 一次 `/chat/completions`，没有工具循环 | 快照按路径排序，整份放进提示词 | 不能现场查。答案写在 `FINAL ANSWER:` |
| T2 | LangGraph `create_agent` | `list_skills`、`read_skill`、`read_skill_reference`、`list_reference_files`、`search_skill_cases`、`list_knowledge_files`、`search_knowledge`、`read_knowledge_file` | `list_knowledge_bases`、`hybrid_search`。没有写文件工具 |
| T3 | smolagents `CodeAgent` | 解释器放行 `json`、`pathlib`，用 `pathlib` 读快照 | 注册同两个只读工具。不放行 `pyosis` |
| T4 | OpenHands 默认智能体 | `load_skills_from_dir`，先 `invoke_skill`。另有官方 `terminal`、`file_editor`、`task_tracker`。浏览器关闭 | 再加同两个只读工具 |
| T5 | CrewAI：检索、作答、复核 | `Crew(skills=...)` 的 `load_skill`。它只返回 `SKILL.md`，用 `read_skill_resource` 读快照里的其余文件。三个角色都能读技能目录 | 三个角色都能调用同两个只读工具。作答者可用 `FileWriterTool` 写笔记，复核者只读。代码执行关闭。允许委派 |
| T6 | 父仓库 OpenCode 一次会话 | 用父仓库已经打开的服务上的技能，不在本仓库另挂一份 | 会话自己的工具，包括它原有的检索。实验仓库不改它的权限 |

## 为什么各框架能力不同

比较的是各框架自己的动作接口。问答要查的知识库，对有工具循环的 T2–T5 用同一对只读函数：`list_knowledge_bases`，然后 `hybrid_search`。它们直接请求检索接口，不建 WeKnora 会话，也不调用 `agent-chat`。未设置 `WEKNORA_API_KEY` 时，从父仓库 `.agents/opencode.json` 的 `mcp.weknora.environment` 读取密钥和地址。环境变量若已设置，则以环境变量为准。

- T1 没有工具循环，不能在回答过程中查库，所以整份本地快照放进这一次提示词。
- T2 的 `create_agent` 不自带工具。调用方传入的是读本地快照，加上上面那两个检索函数。没有写文件，也没有运行 OSIS。
- T3 的动作仍是 Python 解释器，另外注册了这两个检索工具。允许导入只有 `json` 和 `pathlib`。这里不放行 `pyosis`，因为问答不建模型。
- T4 保留 OpenHands 自己的终端和文件编辑器，检索函数加在这套官方工具旁边。
- T5 在同一次 `kickoff` 里检索、写笔记、复核。CrewAI 1.15 的代码解释器已废弃，打开开关也不会注册工具，所以保持关闭。`read_skill_resource` 只补 `load_skill` 读不到的同一份快照。
- T6 不把这两个函数再包一层。它调用父仓库 `datasets/qa/run_eval.py` 的 `chat_via_agent`，技能和检索都在已经运行的 OpenCode 上。实验仓库不改 bash、编辑或外部目录权限，也不复制带密钥的 `opencode.json`。题面仍只有系统提示和 `Question`。评分仍在会话结束后，由本仓库抽取 `FINAL ANSWER:`。
